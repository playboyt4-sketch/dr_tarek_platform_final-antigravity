# Membership Audit — Source Notes

## Approved source hierarchy

- `00_MASTER_ARCHITECTURE.md`, v1.2, Approved: highest reference. Clean Architecture, Feature-First, Repository Pattern, DI, single source of truth; UI must not contain business logic; widgets must not access Firestore directly; all data passes through repositories; premium features and permissions are database/data-driven; no hardcoded business rules. Role enum mapping: `new_student`, `student`, `teacher`, `admin`. Monetization rules belong to Monetization document; subject-based membership plans; device limit is plan-based; feature availability is controlled from Firestore; every user action is logged.
- `01_Project_Vision.md`, v2.0, Approved: student access is governed by assigned permissions/subscription plan; Teacher (Platform Owner) has full access and manages subscriptions/monetization; Admin supports operations but does not have ownership privileges; online payments/subscription management are future expansion themes, with offline learning now V1 per revision.
- `02_Product_Requirements__PRD.md`, v1.3, Approved: approved students access content according to assigned permissions and subscription plan; New Student cannot access educational content/dashboard/exams; Current Student accesses according to plan; Feature 1 approval activates Free Plan automatically; PRD says subscription purchase/renewal/analytics and online payments are Version 1.2 future scope; monetization settings, subscription plans, pricing, and financial options are configured only by Teacher.
- `04_FEATURES.md`, v1.4, Approved, Feature 14: only Student Types `public_student`, `center_student`; plans `public_free`, `center_free`, `center_pro`, `center_max`; Student Type assigned only by Admin/Teacher and students cannot change it. Public gets public_free only; Center gets center_free/pro/max. Operations: upgrade, downgrade, renewal, gift, freeze, resume, public↔center conversion. Changes preserve student progress, notes, quizzes, exams, analytics, history. All capabilities independently controlled by Feature Matrix; no hardcoded permissions. Device limits: public_free 1, center_free 1, center_pro 1, center_max 2+ configurable from dashboard; enforced via `plan_features` and `onLoginAttempt`, Center Max limit change requires Teacher approval. Membership analytics required for type distribution/conversions/upgrade/downgrade/renewal/expired/active.
- `05_DATABASE.md`, v1.6, Approved: `users.student_type` stores `public_student`/`center_student`; student type determines selectable plans; Admin/Teacher conversion preserves all learning data and logs Analytics. Flow: approved Student with type → default Free Plan available implicitly → subject subscription created on first subject access or upgrade → platform access. Free plan activation: backend creates subject-scoped subscription if none exists using matching free plan and `system_settings.default_plan`; maintains one active subscription per student+subject. Membership is subject-scoped. Supported operations same as Feature 14. Device limit is plan-based and binding enabled. Every membership operation produces Analytics. Relevant collections/fields include users, subscriptions, plans, plan_features, devices, analytics_events (to be audited in later ranges).

## Current Flutter implementation evidence

- `lib/features/membership/domain/entities/membership_plan.dart`: `MembershipPlan` contains `id`, `planName`, `planKey`, `studentType`, `displayOrder`, `isActive`; no duration/pricing/marketing metadata.
- `lib/features/membership/domain/entities/plan_feature.dart`: `PlanFeature` contains `id`, `planId`, `featureKey`, `enabled`, and dynamic `featureValue`; this is a generic row model.
- `lib/features/membership/domain/entities/student_subscription.dart`: `MembershipSubscription` contains the core approved subscription fields: id, student_id, subject_id, plan_id, duration_type, start/end dates, status, frozen flags/timestamps, gifted fields, renewal_count, previous_plan_id. It also derives an `AcademicTermLifecycle` locally from dates/frozen state.
- `lib/features/membership/data/datasources/membership_remote_data_source.dart`: wraps Cloud Functions `activateFreePlan`, `upgrade`, `downgrade`, `renew`, `freeze`, `resume`, `gift`; then fetches an active subject subscription. Reads active plans by `student_type` and `is_active`, active subscriptions by student+subject+status, and plan features by plan_id. Mapping uses approved subscription fields but assumes `start_date` is a Timestamp and does not add local operation validation or history orchestration.
- Current Flutter data source is therefore a transport/data-access layer; the substantive authorization and mutation rules must be audited in Cloud Functions and Firestore Rules.

## Backend implementation evidence

- `onStudentApproved` (functions/src/index.ts:777-839) validates `student_type` as `public_student` or `center_student`, requires `system_settings.free_plan_enabled`, resolves the configured default plan by `plan_key + student_type + is_active`, reads `device.max_count` from plan_features, and sets custom claims (`role`, `student_type`, `plan_id`, `max_devices`, `approved`, `subscription_status`, `force_password_change`). It does not create a subject-scoped subscription record at approval time.
- `enforceOneSubscriptionPerSubject` (functions/src/index.ts:938-983) fills a semester end_date when missing, then on duplicate active records marks the newly created record deleted and logs an analytics event. This is a post-create trigger rather than a transaction/precondition that prevents the duplicate write.
- `activateFreePlan` (functions/src/index.ts:1674-1746) is callable only by Admin/Teacher, validates student type, subject, free_plan_enabled, default_plan, active matching plan, and existing active subject subscription, then creates a subject-scoped active semester subscription and logs analytics.
- `validateMembershipPlan` and `changeMembershipPlan` (functions/src/index.ts:1816-1850) validate only that the target plan is active and has the same student_type as the student; both upgrade and downgrade call the same mutation helper and do not visibly enforce directionality or public-to-center conversion rules.
- `renew` updates end_date to current term end and increments renewal_count. `freeze` and `resume` mutate frozen fields. `gift` changes the active subscription plan and sets gifted metadata. All are Admin/Teacher-callable and write analytics.
- Authentication token bootstrap for students calls `getUserPlan`, resolves an active subscription or system default plan, reads `device.max_count`, and includes plan_id/max_devices/subscription_status in custom token claims. `onLoginAttempt` uses max_devices claim for device binding.

## UI, consumer, tests, and environment evidence

- `MembershipPlansScreen` in `student_feature_hub_screen.dart:761-794` watches `availablePlansProvider(user.studentType ?? 'student')` and renders only plan name/key cards. The fallback `'student'` is inconsistent with approved `public_student` and `center_student` values. The screen has no current-subscription state, feature matrix details, or mutation actions.
- `membership_repository.dart` exposes reads for plans, features, and subject subscription plus activate-free, upgrade, downgrade, renew, freeze, resume, and gift operations. `membership_repository_impl.dart` forwards these calls to the remote data source; it does not add business-policy orchestration.
- `membership_providers.dart` exposes available plans, active subscription, plan features, and boolean feature access as FutureProviders. There is no visible single entitlement facade spanning video/PDF/exams/chat/notes/other capabilities.
- `VideoEntitlementService` loads the subject subscription and plan features locally, rejects non-active/missing-endDate/outside-term subscriptions, then interprets `video.access`, `video.quality.max`, and `video.quality.*`. `VideoSourceResolver` separately calls `generateBunnySignedUrl`, which repeats server-side subject subscription and feature checks.
- `plan_quality_matrix_screen.dart` is limited to video quality switches and calls `setPlanQualityFeature`; it is not a full Feature Matrix editor.
- The only identified membership-focused automated test file is `test/video_streaming/video_entitlement_test.dart`, covering inactive/expired subscription denial, missing endDate denial, and video quality cap. No direct tests were identified for membership lifecycle operations, student-type conversion, claims synchronization, duplicate-subscription integrity, or security authorization.
- Environment audit: Ubuntu 24.04.4 LTS on Linux x86_64; Flutter 3.47.0 stable; Dart 3.13.0; one connected Linux desktop device; no Android emulator/device or iOS simulator/device. No Flutter tests/builds were run for this audit-only task. The project directory is not a Git repository (`git status` returned fatal: not a git repository).
- `firestore.rules` allows students to read only their own subscriptions, active plans, and enabled plan_features; all client writes to those collections are denied. The rules do not encode subject-plan eligibility, one-active-subscription uniqueness, subscription expiry/freeze semantics, or feature-key value validation.
- `functions/src/index.ts` search found no exported student-type conversion or explicit membership-plan assignment callable; the visible mutation exports are activateFreePlan, upgrade, downgrade, renew, freeze, resume, and gift.

## Planning baseline: official enums and current key consumers

- `05_DATABASE.md` official Student Types are `public_student` and `center_student`; official Plan Types are `public_free`, `center_free`, `center_pro`, `center_max`; subscription statuses are `active`, `expired`, `cancelled`, and `trial`.
- Current literal feature consumers found in code include `video.access`, `video.quality.*`, `video.quality.max`, `offline.mode`, `pdf.access`, and `pdf.download`. The broader Feature 14 capability list includes preview duration/lectures, video quality, offline, video download, PDF access/download, quiz, exam, notes, chat, PIP, export, notifications, security features, resume video, playback speed, timeline quiz, revision section, final review section, and max devices. The audit plan must reuse existing keys and report any missing/inconsistent keys rather than silently rename them.
- `05_DATABASE.md` analytics event types include membership and operational events such as Membership Upgraded, Membership Downgraded, Membership Renewed, Membership Frozen, Membership Resumed, Gift Membership, Convert Student Type, and Unauthorized Device Attempt.
