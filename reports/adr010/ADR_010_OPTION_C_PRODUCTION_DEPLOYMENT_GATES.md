# ADR-010 Option C — Production Deployment Gates (Phase 0)

Status: Phase 0 deliverable — governance definition only.
**No deployment is authorized by this document.**
Date: 2026-11-17
Companion documents:
`ADR_010_OPTION_C_IMPLEMENTATION_BASELINE.md`,
`ADR_010_OPTION_C_DOCUMENT_IMPACT_MATRIX.md`,
`ADR_010_OPTION_C_DEPENDENCY_AND_PHASE_PLAN.md`

Each gate below is independently approvable and independently reversible. Approving
Gate N does not approve Gate N+1. Approving a Staging execution does not approve a
Production execution.

---

## 0. Global rules that apply to every gate

| Rule | Statement |
|---|---|
| R-01 | `.firebaserc` default is `dr-tarek-platform` (Production). Every command must pass `--project` explicitly. A command without `--project` is treated as a Production command and is forbidden unless the gate being executed is a Production gate. |
| R-02 | Staging (`dr-tarek-staging`) executes before Production for every gate that has both. A gate is not "passed" until the Staging execution has passed and its evidence is retained. |
| R-03 | No gate may read, print, copy, or log a secret payload. Verification uses metadata (`gcloud secrets versions list`, IAM policy, function `secretEnvironmentVariables`), never `versions access`. |
| R-04 | No gate may call a Bunny key-reset endpoint. No gate may activate or configure library `775315`. |
| R-05 | Every gate has a written rollback that was validated in Staging. A gate without a validated rollback is not executable. |
| R-06 | `APP_CHECK_ENFORCEMENT` must not change as a side effect of any gate. It is `false` on all 83 functions today; changing it is a separate, explicitly approved decision. |
| R-07 | No gate may modify data that is not named in its "Resources affected" list. |
| R-08 | The gate owner records the exact revision/deployment id before and after execution. |

### Gate summary

| Gate | Name | Target | Reversible? | Approver |
|---|---|---|---|---|
| G1 | Secret Manager and IAM | Production | Yes (disable version) | Platform Owner |
| G2 | Cloud Functions | Staging → Production | Yes (revision rollback) | Platform Owner |
| G3 | Firestore indexes | Production | Partially (delete index) | Platform Owner |
| G4 | Firestore Rules | Staging → Production | Yes (rules release rollback) | Platform Owner |
| G5 | Dashboard Hosting | Staging → Production | Yes (release rollback) | Platform Owner |
| G6 | Flutter release | Store channels | **No** (binary is irrevocable) | Platform Owner |

## G1 — Secret Manager and IAM

| Field | Value |
|---|---|
| **Target project** | `dr-tarek-platform` (606744934510), region-agnostic |
| **Resources affected** | Secret Manager secrets; IAM policies on those secrets |
| **Expected changes** | (a) Create `BUNNY_ACCOUNT_API_KEY` **only if** B-01 resolves to N2-a. (b) Create `BUNNY_ASSOCIATION_RECEIPT_KEY` (always, for N5). (c) Add exactly one `roles/secretmanager.secretAccessor` binding per new secret to `606744934510-compute@developer.gserviceaccount.com`. (d) Optionally disable `BUNNY_STREAM_API_KEY` v1 (dead value) — separate approval. |
| **Explicitly non-target** | All existing secret versions (no new version, no rotation, no destruction); `BUNNY_TOKEN_KEY`; `BUNNY_PLAYBACK_URL_TEMPLATE`; all `BUNNY_STORAGE_*`; any Bunny-side setting |
| **Preconditions** | Phase 1 U-01/U-02 answered (for the account credential); B-01 decided; `08` secret-naming standard approved; the payload is generated by the Owner in the Bunny dashboard and typed directly into the `gcloud secrets versions add` prompt — never into a file, shell history, or chat |
| **Expected verification** | `gcloud secrets list` shows the new name; `gcloud secrets versions list <name>` shows exactly one `enabled` version; `gcloud secrets get-iam-policy <name>` shows exactly one binding and one member; no payload appears in any transcript |
| **Tests** | (1) Metadata check as above. (2) Negative test in Staging: a function without the binding must fail with a permission error, not silently succeed. (3) Fingerprint check: the Owner confirms the stored value matches the dashboard value by comparing a 4-character prefix + length, not the value. |
| **Rollback** | Disable the new version (`gcloud secrets versions disable <name> --version=1`) and remove the IAM binding. The secret name may remain with zero enabled versions; it is inert. No function reads it until G2. |
| **Risk** | A full-access account key (N2-a) stored in Secret Manager is a high-value credential. Mitigation: single IAM binding, no export, no local copy, and a documented rotation procedure. |
| **Exact owner approval** | "I approve Gate 1 for the Production project dr-tarek-platform: create the secret(s) named ______ and grant `roles/secretmanager.secretAccessor` on each to `606744934510-compute@developer.gserviceaccount.com` only. No other secret, version, IAM binding, or Bunny setting may change. This approval does not authorize deploying any function." |

**Blocked if B-01 is unresolved** for the account credential. The receipt key is not
blocked and can be created independently.

## G2 — Cloud Functions

| Field | Value |
|---|---|
| **Target project** | `dr-tarek-staging` first, then `dr-tarek-platform` |
| **Resources affected** | Only the functions named in the approved change list. Current Production inventory is 83 functions; the baseline for rollback is that inventory. |
| **Expected changes** | New: registration and revocation callables (W09), daily verification scheduler (W11). Modified: `validateBunnyVideoAssociation` and `associateBunnyVideoToLibrary` (dual-verify receipt, N5), `generateBunnySignedUrl` / `getLectureResources` / `getSectionDisplayMedia` (per-library resolution hardening, if needed), `listEligibleBunnyLibraries` (catalog shape). `uploadBunnyResource` is **not** touched unless W12 explicitly includes it. |
| **Explicitly non-target** | The other ~75 functions; `APP_CHECK_ENFORCEMENT`; any function's memory/timeout/concurrency unless listed; Firestore data; Bunny settings |
| **Preconditions** | G1 complete; `05` approved (B-04); Phase 4/5/6 code merged; Staging regression green; every modified function has a captured pre-deploy revision |
| **Pre-deploy capture** | Record the exact revision of every function in the change list. Known-good Production revisions at baseline: `generatebunnysignedurl-00035-vuy`, `getlectureresources-00031-guj`, `getsectiondisplaymedia-00004-rab`, `generatebunnyresourceurl-00017-vom`, `validatebunnyvideoassociation-00001-dab`, `associatebunnyvideotolibrary-00001-rer`. |
| **Tests** | (1) `gcloud functions list` diff = exactly the approved set. (2) `APP_CHECK_ENFORCEMENT` still `false` on all functions, `true` count still 0, malformed still 0. (3) Secret bindings on each function match the approved list exactly (no extra secret, no stale version). (4) Functional: register a library in Staging, play a video from it, revoke it, confirm playback fails closed. (5) Kill-switch test: engage the emergency list and confirm the non-default library becomes ineligible. (6) Receipt transition test U-07. |
| **Rollback** | Redeploy the captured previous revision per function (`gcloud functions deploy <name> --source=<previous artifact>` is **not** available for Gen1 rollback by revision; the rollback method is the one validated in Mission 23: redeploy the previous source/container and confirm the revision id). Rollback is per-function, not all-or-nothing, so a single bad function does not require reverting the set. |
| **Risk** | A partial deployment leaves the set inconsistent (e.g. new validator with old signer). Mitigation: deploy in dependency order — signer/verifier pair together, then registration, then verification job — and test the pair before proceeding. |
| **Exact owner approval** | "I approve Gate 2 for the Production project dr-tarek-platform: deploy only the following functions — ______ — with the secret bindings listed in the approved manifest. No other function, environment variable, `APP_CHECK_ENFORCEMENT` value, Firestore resource, or Bunny setting may change. Rollback is authorized to the captured previous revisions if any post-deploy test fails." |

## G3 — Firestore indexes

| Field | Value |
|---|---|
| **Target project** | `dr-tarek-platform` (and `dr-tarek-staging` first) |
| **Resources affected** | Composite indexes and field configurations only. Baseline: 36 composite indexes; 2 field configs (`__default__` wildcard, `retries/status` COLLECTION_GROUP). |
| **Expected changes** | Add composite indexes **only if** a catalog or audit query requires one. Candidate: `bunny_libraries` ordered by `display_name` (single-field, no composite needed); `bunny_libraries` filtered by `status` + ordered by `last_verified_at` (composite). No change to `__default__` or `retries/status`. |
| **Explicitly non-target** | Existing 36 indexes; field configurations; Rules; data |
| **Preconditions** | G2 deployed with the query in place, or the query identified in code review; `05` approved |
| **Tests** | (1) `gcloud firestore indexes composite list` diff = exactly the approved additions, all `READY`. (2) The query that required the index returns in < 1 s with no `FAILED_PRECONDITION`. (3) No existing index enters `ERROR`. |
| **Rollback** | Delete the added index. Index deletion is safe; it can only make the dependent query fail, which is a functional regression, not a data loss. |
| **Risk** | An index build can take time on a large collection; `bunny_libraries` is empty, so risk is negligible today. |
| **Exact owner approval** | "I approve Gate 3 for the Production project dr-tarek-platform: create only the following Firestore indexes — ______. No existing index or field configuration may be modified or deleted." |

**May be a no-op.** If no Option C query requires a composite index, Gate 3 is recorded
as "not required" with the query analysis as evidence.

## G4 — Firestore Rules

| Field | Value |
|---|---|
| **Target project** | `dr-tarek-staging` first, then `dr-tarek-platform` |
| **Resources affected** | `firestore.rules` only |
| **Expected changes** | Option C should require **no** client-facing change: `bunny_libraries` stays deny-all (all access via callables), and `lecture_resources` keeps `bunny_library_id` immutable and backend-only. The only possible change is an explicit `isDoctor()` read path **if** the Dashboard reads the catalog directly instead of through a callable — which is not the recommended design. |
| **Explicitly non-target** | Every other `match` block; Storage rules; indexes |
| **Preconditions** | G2 deployed; `05` approved; a Rules unit-test suite covering the catalog and resource gates exists and passes |
| **Tests** | (1) Rules unit tests: client read of `bunny_libraries` denied; client write denied; client create of `lecture_resources` with `bunny_library_id` set is denied; update attempting to change `bunny_library_id` is denied; Doctor/admin paths behave as specified. (2) Production Rules diff is empty or exactly the approved lines. (3) Smoke: student playback, admin resource creation, and library listing all succeed through their intended path. |
| **Rollback** | `firebase deploy --only firestore:rules` with the captured previous rules file; rules releases are versioned, so the previous release can be restored. |
| **Risk** | A permissive catalog read would expose library ids and hosts to any signed-in user. This is why the recommended design is deny-all + callable. |
| **Exact owner approval** | "I approve Gate 4 for the Production project dr-tarek-platform: deploy `firestore.rules` with the diff shown, which changes only ______. No other rule block may change." |

## G5 — Dashboard Hosting

| Field | Value |
|---|---|
| **Target project** | `dr-tarek-staging` first, then `dr-tarek-platform` |
| **Resources affected** | The Dashboard Hosting site only |
| **Expected changes** | New screens: library list, registration, revocation, fallback credential entry (masked, one-time), upload with library selection. New callable integrations. No change to existing screens except where a library selector is inserted. |
| **Explicitly non-target** | Cloud Functions; Firestore; Storage; the Flutter student app; DNS/domains |
| **Preconditions** | B-03 resolved (Figma); `03` updated and approved; `15`/`14` permission split approved; `FINAL_DECISIONS` §4 amended (C-01); G2 deployed; `flutter analyze` clean; Dashboard tests at or above the baseline (407 pass / 7 known failures, which must not increase) |
| **Tests** | (1) Doctor can register, verify, and revoke a library. (2) `ADMIN_CONTENT` **cannot** register or revoke (permission negative test). (3) Fallback credential entry is masked, single-use, and never echoed back. (4) Upload shows progress and handles failure/resume. (5) Existing Dashboard flows unchanged (regression). (6) No library id, host, or credential appears in any client-visible error message. |
| **Rollback** | Restore the previous Hosting release (Hosting keeps release history). Because the Dashboard calls G2 callables, a Hosting rollback alone is sufficient only if the callables remain backward compatible; otherwise roll back G2 first. |
| **Risk** | A Dashboard rollback that leaves new callables deployed is safe (unused). The reverse — old Dashboard calling removed callables — is not. Therefore: deploy callables before the Dashboard, and roll back the Dashboard before the callables. |
| **Exact owner approval** | "I approve Gate 5 for the Production project dr-tarek-platform: deploy the Dashboard build at commit ______ to Hosting. No Function, Firestore, Storage, or domain change is authorized by this approval." |

## G6 — Flutter release

| Field | Value |
|---|---|
| **Target** | The student app release channel(s) currently in use |
| **Resources affected** | The published app binary; any `--dart-define` values compiled into it |
| **Expected changes** | Multi-library playback support (the client does not need to know the library — it receives a signed URL), library-aware error states, and no credential handling of any kind in the client. **The client must never receive a library id, a host, or a key.** |
| **Explicitly non-target** | Backend; Dashboard; Firestore |
| **Preconditions** | G2, G4, G5 passed; Phase 7 regression green; the `--dart-define` default library id is confirmed per environment (Amendment 1); no fallback to a hardcoded `736742` |
| **Tests** | (1) Playback from ≥2 libraries on a real device. (2) Playback failure message does not leak library identity. (3) Offline/expiry behaviour unchanged. (4) The compiled binary contains no library id or key beyond the documented `--dart-define` default. |
| **Rollback** | **None for the binary.** A store release cannot be un-published. Mitigation: staged rollout (if the channel supports it), a kill switch via the emergency list (which requires G-01 to be resolved so the default library can also be disabled), and a server-side playback gate. |
| **Risk** | Irreversibility. This is the only gate with no true rollback, which is why it is last and why G-01 (default-library kill switch) matters before it ships. |
| **Exact owner approval** | "I approve Gate 6: release the Flutter build at commit ______ to ______ with the `--dart-define` values ______. I understand this release cannot be revoked once published." |

## 5. Gate-level stop conditions

Any of these halts the gate in progress, regardless of prior approvals:

| Condition | Action |
|---|---|
| An Approved document is found to conflict with the change being deployed | Stop; report the conflict; do not deploy |
| A required credential is missing at execution time | Stop; do not substitute a different credential |
| The change would require modifying a Production resource outside the gate's "Resources affected" list | Stop; request a new gate |
| The Production function inventory or `APP_CHECK_ENFORCEMENT` distribution differs from the baseline (83 / false×83) in a way not explained by an approved change | Stop; re-baseline |
| A rollback path cannot be validated | Stop; the gate is not executable |
| Any secret payload would have to be displayed to proceed | Stop; redesign the verification |
| Any step would touch library `775315` or call a Bunny key-reset endpoint | Stop; forbidden |

## 7. Non-authorization statement

**No deployment is authorized by this document.** Phase 0 performed no deployment, no
secret creation, no IAM change, no index change, no Rules change, no Hosting change, and
no app release. The six gates above are a proposed governance structure for future
missions; each requires its own explicit Platform Owner approval at the time of
execution.
