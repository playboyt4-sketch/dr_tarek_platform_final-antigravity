**Audit type:** independent, evidence-based, audit-only

**Working tree:** uncommitted Mission 1–4 work (28 modified tracked files, 24 untracked)

---

## 1. Executive verdict

# BLOCKED

Two independent blocking conditions exist. Either one alone is sufficient to
block a production deployment.

1. **CRITICAL — `created_at` is mutable on update.** The `lecture_resources`
   update rule does not constrain `created_at`. A content manager can backdate a
   post-cutover (pending) row to any date before the cutover, or set it to
   `null`, which reclassifies it as a legacy row. The playback gate then falls
   back to the default library and issues playback for a video whose association
   was never verified by `validateBunnyVideoAssociation`. This was proven with a
   live Firestore-emulator probe (section 4.1). The Mission 4 claim that
   "back-dating is now denied" is true only for `create`, not for `update`.
2. **HIGH — the ADR-010 implementation gate is not met.** ADR-010 forbids
   deployment or migration until *every* existing video resource has a verified
   library mapping. The repository contains only a read-only migration planner
   and a dry-run CLI; `--apply` is explicitly refused. The inventory shows 13
   video resources, of which 3 point at the inactive library `775315` and 7 have
   no usable Video ID. No write executor exists.

Additional release-relevant gaps (non-blocking on their own): the Dashboard
library picker required by ADR-010 is not implemented (new rows always target
`736742`); the built-in cutover default has already elapsed, so an unconfigured
deploy makes all newly authored rows pending; the Mission 4 recommended
deployment order (Functions first, Rules second) leaves a persistent
self-assignment window; and there is no Rules test for update-backdating.

Verdict: **do not deploy** until finding C-1 is fixed (with tests) and the
ADR-010 implementation gate is satisfied or explicitly waived by the Platform
Owner with a written migration decision.

## 3. Findings

### CRITICAL

**C-1 — `created_at` update bypass reclassifies pending rows as legacy**
`firestore.rules:317-324`. The update rule checks `bunny_library_id`,
`resource_type` and `bunny_video_id`, but never `created_at`. The create rule
(`314-316`) does require `created_at == request.time`, and every legitimate
authoring path writes `FieldValue.serverTimestamp()`, so create is correct. The
update path is not.

Impact chain:
`created_at` is the **only** legacy/pending discriminator
(`bunny_library_association.ts:173-179`). Backdating a pending row (or nulling
`created_at`) makes `isBunnyAssociationRequired` return `false`;
`mayResolveBunnyLibraryForPlayback` (`189-197`) then allows the default-library
fallback, and `generateBunnySignedUrl` (`index.ts:4537-4548`) issues playback.
The same update rule also allows `bunny_video_id` to change while the stored
library is `null` (`321-323`), so the attacker can both reclassify the row and
point it at an unverified video.

Proof: `D:\Temp\opencode\probe_backdate.js` (outside the repository, run against
the local Firestore emulator with the repository rules). Output:

```
STEP1 create with created_at = request.time        ALLOWED (expected)
STEP2 update created_at -> 2020-01-01T00:00:00Z    ALLOWED  <-- BYPASS
STEP3 update created_at -> null                    ALLOWED  <-- BYPASS
final created_at: null
```

Smallest correct fix (not implemented): add
`&& request.resource.data.get('created_at', null) == resource.data.get('created_at', null)`
to the update rule, and add update-backdate and `deleteField()` cases to
`security-tests/adr010_association_rules.test.js` (currently only the create
case exists, at lines 138-142).

### HIGH

**H-1 — ADR-010 implementation gate unmet (mapping/backfill)**
`21_ADR_010_Multi_Library_Bunny_Stream.md:150-157` requires a verified mapping
for every existing video resource before deployment. `bunny_library_migration.ts`
is a planner only (`:8-9`, `:98-99`); `backfill_bunny_library_id.ts` refuses
`--apply` (`:1-18`, `:128-134`). Inventory
(`reports/adr010/bunny_resource_inventory.md`): 13 video resources, 3 in
`775315`, 3 in `736742`, 7 without usable IDs. Deploying now either leaves those
rows pending (unplayable) or, if the cutover is set late, silently plays them via
the default library — which is precisely the ambiguity the ADR exists to remove.

**H-2 — Dashboard library picker not implemented**
ADR-010 (`:100-109`) requires selecting an existing configured library and
storing it. Only non-visual scaffolding exists
(`bunny_library_catalog.dart`, `bunny_library_association.dart`); new Dashboard
rows always resolve to `defaultBunnyLibraryId` (`subject_details_provider.dart:936-940`).
The multi-library capability is therefore not operable from the Dashboard, and
`775315` content cannot be authored or re-pointed through the UI.

**H-3 — Cutover default already elapsed; sequencing can create a window**
`BUNNY_ASSOCIATION_CUTOVER_DEFAULT = "2026-11-13T00:00:00.000Z"`
(`bunny_library_association.ts:45`) is in the past (audit at ~09:51 UTC on
2026-11-13). Consequences:
- Deploying without an explicit `BUNNY_ASSOCIATION_CUTOVER` marks every row
  authored today (and later) pending. Today's legitimately authored content
  becomes unplayable until the callable succeeds.
- Mission 4 recommends **Functions first, Rules second** (`mission_4_final_report.md:277-298`).
  Under the old Rules, a client may write `bunny_library_id` directly. Because
  the playback gate accepts any non-null stored library
  (`bunny_library_association.ts:194-195`), a content manager can persist an
  unverified association that survives the Rules deploy and is accepted by the
  new Functions. The registry fail-closes unknown/inactive IDs, so the practical
  escalation is limited to the default library — but it defeats the
  "server-verified" invariant and is avoidable.
- Rules-first (or atomic) is safer: the new Rules block client writes
  immediately, and a row that the old Functions cannot yet gate is still
  protected by the Rules from forgery.

**H-4 — No Rules test for update-backdating**
`security-tests/adr010_association_rules.test.js` has 15 assertions; only
create-backdating is covered (138-142). The CRITICAL defect passed because the
suite mirrors the implementation's blind spot.

### MEDIUM

**M-1 — Dashboard create failure loses the entered Video ID**
Dashboard creates the row with `bunny_video_id: null`
(`subject_details_provider.dart:1150-1159`) and only the callable writes the
Video ID (`bunnyAssociationWriteFields` = video id + library id). If the callable
fails, the pending row has no pointer, so a retry requires re-entering the Video
ID. Quick Upload and mobile retain the pointer on the row
(`quick_upload_modal.dart:435-455`,
`admin_content_remote_data_source_impl.dart:663-695`), so retries there are safe.
Recommendation: write the pointer at create (Rules allow it on unverified rows),
then let the callable confirm/overwrite.

**M-2 — `first_video` metadata inconsistency**
Mobile `_syncLectureFirstVideo` (`admin_content_remote_data_source_impl.dart:143-183`)
and `scripts/backfill_first_video.cjs` omit `bunny_library_id`, while the
Dashboard and the server include it
(`firstVideoFieldsFromResources`, `index.ts:8728-8772`). The server recomputes
`first_video` on association, so this is a hint/metadata divergence, not a
playback authority bug — but it produces inconsistent documents and can mislead
clients that read the hint.

**M-3 — `BUNNY_STREAM_API_KEY` is in plain `functions/.env`**
ADR-010 (`:80-81`) requires library credentials in Secret Manager. The file is
gitignored and untracked, and was not exposed in this audit, but it is not
managed by the documented secret mechanism. `BUNNY_TOKEN_KEY` and the playback
template are Secret Manager–backed. Governance/ops gap, not a leak.

**M-4 — Lint/CI gate is red at HEAD**
`npm run lint` (functions) exits `1` with 9,482 problems (9,463 errors, 19
warnings). 9,452 are `linebreak-style` (CRLF on Windows). Excluding linebreak
style: 12 non-linebreak errors at HEAD, 14 in the worktree; Mission 4 adds
`operator-linebreak` errors at `index.ts:5069-5070`. CI lint was already red
before this work, but the workstream adds to it. Deployment does not require
lint, yet the release gate cannot be claimed green.

**M-5 — CI workflow not executed**
`.github/workflows/ci.yml` adds an `adr010-emulator` job with fake fixture
secrets. It was reviewed but **not run** (no push authorized). CI status is
therefore unknown, not "passing".

### LOW

**L-1 — Error reasons disclose planning detail**
`associateBunnyVideoToLibrary` returns `Bunny library association rejected (${planned.reason})`
(`index.ts:5073`, `5127`). Callers are authenticated content managers, and the
reason codes are non-secret, but they do enumerate the server's checks.

**L-2 — Receipt is replayable within TTL onto the same resource**
TTL is 600 s; signature binds resource/lecture/library/video
(`bunny_library_association.ts:241-256`). Replay onto the same resource is
idempotent by design; replay onto any other identity fails signature
verification. Acceptable; documented as intentional.

**L-3 — Pre-existing, unrelated test failures**
`subject_details_test.dart` and `subject_grade_context_sync_test.dart` fail
(17 passed / 7 failed, text-alignment assertions). Both files are unmodified in
the worktree, so these are pre-existing and unrelated.

**L-4 — Known content issues remain**
Archived lectures are still issuable; one duplicate Video ID exists; 7
placeholder rows; the `775315` pull zone remains unsigned HLS. All are outside
ADR-010 scope and must not be "fixed" silently.

### INFO

- `created_at == request.time` on create is compatible with **all** legitimate
  paths: Dashboard add, Quick Upload, mobile create, and server-side writes all
  use `FieldValue.serverTimestamp()`. Verified by inspection and by the create
  case in the rules suite.
- `getEnv`, HMAC construction, constant-time comparison, TTL, transaction
  re-read, idempotent write of exactly two fields, and the
  `requireContentManager` authority check (`index.ts:7523-7550`) are correct.
- Registry fail-closed behavior is correct: `775315` is defined but inactive
  (`bunny_library_registry.ts:74-81`, activation `171-178`), unknown/inactive
  libraries are rejected, and cache keys include the library
  (`128-133`).
- The library hint from the client cannot select credentials: with a stored
  value it is compared and must agree; without one it is ignored
  (`bunny_library_registry.ts:21-23`, `195-233`).
- Display media (poster/preview) uses the same per-library resolution and the
  same gate (`index.ts:1629-1657`, `1837`), so display cannot diverge from
  playback.
- `reports/` is untracked, so this report is a new artifact and not a change to
  governed documentation.

## 6. Security and Firestore Rules assessment

Verified correct:

- Only content managers (`canManageContent`) can create/update; doctor and
  content permission paths unchanged; reads unchanged for approved content,
  doctors, and content managers.
- Clients cannot set `bunny_library_id` on create (`314-316`).
- Clients cannot change or remove `bunny_library_id` on update (`317-318`).
- Clients cannot change `bunny_video_id` on a verified row (`320-323`).
- Clients cannot change `resource_type` (`319`).
- Delete remains denied (`325`).
- `created_at == request.time` holds for every legitimate create path.

Not verified / defective:

- **`created_at` is mutable on update** (C-1). This is the security boundary
  because it is the only discriminator between legacy and pending.
- Rules tests do not cover update-backdating or field removal (H-4).
- Server callable authorization, HMAC, TTL, resource binding, replay, and
  transaction consistency are correct; error text leaks only reason codes (L-1).
- No client-controlled credentials or Pull Zone selection: the registry resolves
  credentials from server env only, and the client library hint is
  compare-and-ignore (INFO).

## 7. Playback and cutover assessment

- Pending rows (post-cutover, no stored library) are refused with
  `failed-precondition` (`index.ts:4537-4548`).
- Legacy fallback applies only when `created_at` is unreadable or strictly before
  the cutover (`173-179`). **This is exactly the predicate C-1 forges.**
- A stored library short-circuits the gate (`194-195`); the registry then
  fail-closes unknown/inactive libraries. This is safe only if Rules prevent
  client writes — hence Rules-first deployment.
- Cache keys include the library ID (`128-133`); display media uses the same
  resolution and gate (`1629-1657`, `1837`).
- `775315` is defined but inactive; activation requires the allow-list env
  (`171-178`) and no client input can activate it.
- `736742` behavior is preserved: default ID, default fallback, same signing
  path.
- Entitlements, preview limits, quality matrix, device binding, playback
  takeover, ordering, and first-video semantics are untouched by this change set
  (the diff adds library plumbing, not authorization changes).

Cutover mechanics:

- Defined at `bunny_library_association.ts:44-45`; overridable via
  `BUNNY_ASSOCIATION_CUTOVER`; malformed values fall back to the default.
- All consumers use the same resolver (`bunnyLibraryEnvSnapshot()` +
  `resolveBunnyAssociationCutoverMs`), so policy is consistent.
- Before cutover: rows are legacy, default fallback applies.
- At/after cutover: rows must carry a verified association.
- Deployment risk: the default instant has passed; Functions-first leaves the
  Rules window described in H-3.

1. Fix C-1 in `firestore.rules` and add update-backdate/`deleteField` tests;
   re-run the rules suite and the probe.
2. Satisfy the ADR-010 implementation gate: verified mapping for all 13 video

## 11. Deployment sequence (recommended, not executed)

1. Take a Firestore export/backup of `lecture_resources` and `lectures`.
2. Deploy **Firestore Rules first** (with the C-1 fix) and verify with the rules
   suite against the deployed project.
3. Set `BUNNY_ASSOCIATION_CUTOVER` to the intended instant in the Functions
   environment; confirm all function instances read the same value.
4. Deploy Functions (validation, association, playback gate, display media).
5. Deploy Dashboard and mobile builds that stop writing `bunny_library_id` and
   call the gateway.
6. Smoke-test: verified row plays; pending row is refused; legacy row plays via
   default; `775315` is rejected; poster/preview matches playback.
7. Monitor `failed-precondition` rates and association-callable failures.

Rules-first is required because the new gate trusts a stored library and the old
Rules let clients write it.

## 12. Rollback plan (not executed)

- **Rules:** redeploy the previous `firestore.rules`. This immediately restores
  client authoring but also restores the self-assignment window; roll back
  Functions only if the gate is causing an outage.
- **Functions:** redeploy the previous revision (keep the previous revision
  pinned). Old Functions ignore `bunny_library_id` and use the single-library
  signing path, so playback continues; associations already written remain
  harmless metadata.
- **Cutover:** rolling Functions back does not require changing the env; if a
  forward-fix is chosen instead, moving the cutover later immediately restores
  legacy fallback for rows created after the old instant.
- **Data:** restore `lecture_resources`/`lectures` from the export only if an
  association write corrupted pointers; the callable writes exactly two fields,
  so targeted restoration is feasible.
- **Clients:** Dashboard/mobile rollback is safe; both tolerate rows without
  `bunny_library_id`.
